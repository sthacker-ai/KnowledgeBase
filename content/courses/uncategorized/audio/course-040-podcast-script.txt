[ALEX]: If you dump all your PDFs and notes into a raw/ folder without any processing, you’ll still hit a wall when you try to retrieve them later because the system can’t synthesize across documents.
[SAM]: Why can’t a simple full‑text search across raw/ give you the synthesized insight you need?
[ALEX]: Search returns matching snippets, but it doesn’t create new connections—like linking a concept from a research paper to a definition you wrote in a meeting note—so you miss the emergent understanding that comes from seeing how ideas relate.
[SAM]: So the wiki/ layer is where those connections are built. How does the AI actually turn a single raw file into multiple wiki pages?
[ALEX]: The ingestion step just copies the source into raw/. Then a processing pipeline runs: it reads each file, extracts entities and claims, and prompts an LLM to elaborate each claim into a self‑contained note that links to any related entities already in the wiki.
[SAM]: Can you give a concrete example of what gets extracted and how the LLM expands it?
[ALEX]: Suppose you drop a PDF of a climate‑change report into raw/. The pipeline might pull out the claim “global CO₂ emissions rose 1.5 % in 2023.” The LLM then writes a wiki page that explains why that rise matters, cites the source, links to pages on “carbon budget,” “renewable adoption,” and even creates a new page for “2023 emissions data” if it doesn’t exist yet.
[SAM]: That sounds like one source spawning many pages. Does the system ever duplicate effort if the same claim appears in two different raw files?
[ALEX]: It checks the wiki for an existing page with a matching canonical title; if found, it adds a backlink from the new source instead of rewriting the page, preserving a single source of truth for each concept.
[SAM]: How do you decide what constitutes a “canonical title” for a page?
[ALEX]: We use a deterministic slug based on the normalized entity name—lowercase, hyphen‑separated, stripping articles—so “Global CO₂ emissions” and “CO₂ emissions worldwide” both map to the same slug “global-co2-emissions.”
[SAM]: What about the raw data itself? Do we ever edit those files, or are they truly immutable?
[ALEX]: The raw/ folder is treated as immutable; we never modify the original PDFs or notes. Any corrections go into the wiki/ layer as a separate note that references the raw source, keeping the provenance clear.
[SAM]: If raw/ stays unchanged, how do you handle version updates when you get a newer edition of a source?
[ALEX]: You add the new file as a separate entry—perhaps with a date or version suffix—and the pipeline treats it as another raw item. The wiki can then link both versions, showing evolution over time.
[SAM]: Let’s talk about scalability. If I have thousands of raw files, does the LLM step become a bottleneck?
[ALEX]: Yes, the LLM call per extracted claim is the main cost. We mitigate it by batching claims, caching LLM responses for identical prompts, and running the process incrementally—only new or changed raw files trigger fresh LLM work.
[SAM]: Incremental processing sounds useful. How does the system know which raw files have changed?
[ALEX]: We compute a hash (SHA‑256) of each file when it’s first ingested and store it in a manifest. On each run, we recompute the hash; if it differs, the file is marked for reprocessing.
[SAM]: What happens to the wiki/ when a raw file is deleted or replaced?
[ALEX]: The manifest flags the file as removed; a cleanup pass deletes any wiki pages that were generated solely from that raw file and have no other incoming links, preventing orphaned content.
[SAM]: This seems to require a fair amount of tooling—scripts, a manifest, maybe a database. Is there a minimal viable setup someone could start with today?
[ALEX]: You can begin with a simple folder structure, a Python script that walks raw/, uses a lightweight LLM API (like Llama.cpp) to elaborate claims, and writes markdown files to wiki/. The manifest can be a JSON file; you don’t need a full database until you hit hundreds of files.
[SAM]: Finally, what’s the payoff of keeping raw/ and wiki/ separate beyond traceability?
[ALEX]: Separation lets you experiment freely in wiki/—re‑linking, restructuring, or even deleting pages—without ever risking the loss of the original source material, which remains the verifiable ground truth for any future audit or re‑run of the pipeline.
