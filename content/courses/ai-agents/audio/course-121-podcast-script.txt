[SAM]: How does the workflow actually define those agents in Fable 5? Are they just functions, or is there a specific data structure that enforces the message contract?

[ALEX]: Each agent is a Frecord with two fields: a mutable‑looking but actually immutable state record and a handle function of type Message → State * Message list. The Message type is a discriminated union covering all possible inputs—like GenerateCode, RunLint, UpdateDocs, and Error—so pattern matching in handle guarantees exhaustive coverage and prevents misspelled event names at compile time.

[SAM]: If the state is immutable, how does an agent accumulate knowledge across multiple turns, say when it needs to remember which files it has already linted?

[ALEX]: The handle function returns a new state record that incorporates any updates; the scheduler feeds that returned state back into the agent on the next cycle. Because the state is a plain F# record, you can copy‑and‑modify fields with the { state with … } syntax, giving you a clear audit trail of changes without mutating shared memory.

[SAM]: You mentioned a lightweight scheduler—what does it actually do, and why not just let agents call each other directly?

[ALEX]: The scheduler maintains a queue of incoming messages, dispatches each to the appropriate agent’s handle function based on the Message union tag, collects the outgoing messages, and re‑queues them. This indirection decouples agents: they never know who sent a message or who will receive it, which lets you hot‑swap implementations, add logging, or reroute messages for testing without touching agent code.

[SAM]: What about error handling? If one agent fails, does the whole pipeline crash, or is there a way to isolate faults?

[ALEX]: Errors are modeled as first‑class messages—an Error union case carrying a payload and a traceback. When an agent’s handle throws, the scheduler catches the exception, wraps it in an Error message, and sends it to a dedicated ErrorHandler agent that can log, retry, or escalate. Because errors are messages, they can be inspected, filtered, or replayed just like any other signal.

Development overhead rises slightly because you must design the Message union and keep agents stateless aside from their record, but this pays off in easier debugging, deterministic unit tests, and the ability to scale agents across workers independently on different threads or nodes.

[SAM]: How does persistence work? If the orchestrator restarts, do agents lose their state, or is there a built‑in mechanism to snap‑shot and recover?
